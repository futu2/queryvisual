# QueryVisual I18n Design

## Goal

Add first-pass internationalization to QueryVisual with English and Simplified Chinese support, automatic browser-language detection on first load, and a user-visible language switcher with persisted manual override.

## Scope

This design adds:

- a small in-repo i18n layer with no third-party dependency
- support for `en` and `zh-CN`
- browser-language auto-detection on first load
- persisted manual language override
- a sidebar language switcher
- localization of fixed application and editor UI chrome

This design does not add:

- localization of user-authored data such as graph names, node names, output names, expressions, or table names
- localization of persisted sample workspace content already stored as graph data
- localization of validator/analyzer diagnostic message text
- a broad date, number, or pluralization framework
- server-side locale persistence

## Decisions

- Language selection uses browser auto-detect on first load, then persists manual override in local storage.
- The first pass localizes only fixed UI chrome, not user/workspace content.
- The manual language switch lives in the left sidebar near the save/load controls.
- The implementation uses a small internal i18n layer rather than a third-party library.
- Translation keys are stable message ids, not English strings.
- Missing translations should fail loudly in development/tests but fall back to English at runtime.
- Interpolation is supported only for simple label cases in v1.

## User Experience

On the first app load:

1. If a manually selected locale exists in local storage, use it.
2. Otherwise inspect `navigator.language`.
3. Map Chinese variants to `zh-CN`.
4. Fall back to `en` for all other cases.

The sidebar shows a compact language control near `Save JSON` and `Load JSON`. Changing the language updates the visible UI immediately and persists the selection for future loads.

The language control affects fixed UI labels only. It does not rewrite any existing graph metadata, sample graph labels stored in workspace data, SQL text, or validation output.

## Architecture

### Runtime Model

Add a provider-backed i18n layer in the client:

- `I18nProvider` owns current locale state
- `useI18n()` exposes:
  - `locale`
  - `setLocale(locale)`
  - `t(key, vars?)`

The provider is mounted near the app root so any editor component can translate UI text without prop threading.

### Locale Resolution

Locale resolution is client-only and synchronous enough for app startup:

- local storage key is checked first
- browser language is checked next
- a normalized locale enum is produced:
  - `en`
  - `zh-CN`

Normalization rules:

- any locale beginning with `zh` resolves to `zh-CN`
- all other values resolve to `en`

### Translation Dictionaries

Store translations as typed TypeScript objects in-repo.

Recommended files:

- `src/features/i18n/types.ts`
- `src/features/i18n/messages.ts`
- `src/features/i18n/I18nContext.tsx`
- `src/features/i18n/LanguageSwitcher.tsx`

`messages.ts` should define a canonical dictionary shape and export both locale dictionaries from the same module so missing keys are caught during development.

## Translation Boundaries

### Included In V1

Fixed UI chrome in these areas should be localized:

- app shell headings and descriptive copy
- document toolbar labels and load errors
- graph catalog labels, buttons, active-pill text, and delete-guard alert
- language switcher label and locale option labels
- node palette labels
- modal section headings and confirmation dialog text
- output runtime inspector labels and tabs
- editor field labels, placeholders, button labels, and small helper copy
- node visual chrome labels such as `Inputs`, `Outputs`, and `error`
- option labels for join type, sort direction, graph picker prompt, and similar fixed controls

### Excluded In V1

These remain untranslated:

- graph metadata names
- node labels and names already treated as user/workspace content
- output names
- expressions and SQL
- semantic/IR/diagnostic payload contents
- validation/analyzer diagnostic prose

## Message-Key Strategy

Use stable message ids grouped by feature area, for example:

- `app.title`
- `app.canvasTitle`
- `toolbar.saveJson`
- `toolbar.loadJson`
- `toolbar.loadError`
- `graphCatalog.title`
- `graphCatalog.newGraph`
- `graphCatalog.open`
- `graphCatalog.delete`
- `graphCatalog.active`
- `graphCatalog.deleteBlocked`
- `modal.discard.title`
- `modal.discard.body`
- `outputRuntime.lastRun`
- `outputRuntime.lastError`

Do not use English strings as keys.

Interpolation is allowed for a narrow set of labels, such as:

- `graphCatalog.openNamed`
- `graphCatalog.deleteNamed`

## Component Integration

The first pass should replace hard-coded UI strings incrementally in the visible surface, including at least:

- `src/App.tsx`
- `src/features/document-storage/DocumentToolbar.tsx`
- `src/features/workspace/GraphCatalog.tsx`
- `src/features/graph-editor/NodePalette.tsx`
- `src/features/graph-editor/NodeEditorModal.tsx`
- `src/features/graph-editor/nodeEditors.tsx`
- `src/features/graph-editor/nodes/QueryNode.tsx`

Additional UI components discovered during implementation can be included if they are clearly inside the agreed fixed-chrome boundary.

## Error Handling And Fallbacks

Missing-key behavior should be split by environment intent:

- development/tests:
  - surface missing keys loudly so gaps are caught quickly
- runtime:
  - fall back to the English message if available
  - if even English is missing, render a visible fallback token such as the key itself

This keeps the app usable while still making translation gaps diagnosable.

## Persistence

Use local storage for the manual override only.

Recommended behavior:

- no stored value means "auto-detect mode"
- once a user changes the language, store the explicit locale string

This keeps the model simple while matching the requested UX.

## Testing Strategy

Add focused tests rather than snapshots.

### I18n Layer Tests

- locale normalization from browser values
- persisted locale override wins over browser detection
- missing-key fallback behavior

### UI Tests

- default English rendering when browser locale is non-Chinese or unspecified
- Simplified Chinese rendering after manual switch
- persisted selection survives rerender/provider re-init
- representative components update visible text when locale changes

### Regression Focus

Tests should verify that localization changes only fixed UI chrome and does not alter user/workspace content such as graph names.

## Implementation Notes

- Keep the first pass intentionally small and explicit.
- Avoid introducing a generic formatting subsystem until the app actually needs number/date/plural rules.
- Continue treating content stored in workspace/domain data as user content, not translation material.
- If runtime timestamps are later localized, that should be a targeted follow-up rather than part of this pass.

## Acceptance Criteria

The feature is complete when:

- the app auto-detects English vs Simplified Chinese on first load
- the sidebar exposes a visible language switcher
- manual selection persists across reloads
- fixed application/editor UI chrome is translated in both locales
- user/workspace content remains unchanged
- representative tests cover locale detection, switching, persistence, and visible UI updates
